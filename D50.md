# fm1-d50: a Roland D-50 on the M-VAVE FM-1

Status: a plan. No D-50 code exists yet. This repository starts as a copy of
[fm1-sf2](https://github.com/mwedmark/fm1-sf2) (remote `upstream`, its `main` at `3bf0074`),
because the device side is solved there: the toolchain, the audio hook, the second core, the flash upload, safe mode, the emulator workflow and
the install page. The goal is different: **a faithful D-50 clone that only runs the D-50, at 32 kHz, as close to the original as can be done.**
It is not a GM player, and it has no SoundFont.

Facts about the D-50 below that are marked *(verify)* come from memory and must be checked against the service manual, the owner's manual
and the MIDI implementation before code depends on them. Milestone 1's findings, with sources, are in [RESEARCH.md](RESEARCH.md).

## 1. What the D-50 is (the target)

- **Patch** = Upper tone + Lower tone, a key mode (Whole, Dual, Split, and the Separate / -S variants *(verify the full list)*), split point,
  balance, tone transposes, the patch's reverb type and level, portamento, and the bender and aftertouch assignment.
- **Tone** = Tone Common + **2 partials**. The tone's *structure* (1..7) says how the two partials combine: alone, or through the ring modulator.
  Tone Common also holds the pitch envelope, three LFOs, the EQ (low and high) and the chorus *(verify: 8 chorus types)*.
- **Partial**: the wave generator (a synth wave, square or saw with pulse width and PWM, or a PCM wave), pitch (coarse, fine, key follow,
  the LFO and envelope modes), **TVF** (cutoff, resonance, key follow, bias, its envelope, LFO depth: synth partials only), **TVA** (level,
  velocity, bias, its envelope, LFO depth). The envelopes have times and levels, a sustain point and an end point, and velocity and key-follow
  time scaling.
- **PCM waves**: 100, attack transients and loops, from the 512 KB wave ROM. Their start and length are in tables in the program EPROM.
- **Polyphony**: 32 partials, i.e. 16 voices for a Whole patch, 8 + 8 for Dual *(verify the allocation rules: Roland's voice stealing is part of the sound)*.
- **Rate**: the LA chip (MB87136A, the MT-32's part number) runs from 32.768 MHz, which gives **32 kHz** as in the MT-32 (not measured on a D-50).
  Then come the chorus ASIC, the reverb chip (its 32 types are in the silicon), the D/A and the analog output stage.
- **Control**: a NEC uPD78312 at 12 MHz (8 KB internal ROM, IC25, plus the 64 KB EPROM, IC22) runs Roland's firmware. It reads MIDI and the panel, computes the envelopes and LFOs, and writes the LA chip's
  registers. Most of what makes a D-50 sound like a D-50 (the envelope curves, the key-follow tables, the LFO shapes, the voice allocation) lives in that
  firmware, not in the LA chip.
- **MIDI**: Roland SysEx DT1/RQ1 with the D-50's address map. Patches, tones and partials are bytes at fixed addresses. The patch banks people have
  (`.syx`) are dumps of that memory, and they are the test material.

## 2. How faithful: two ways

| | A: run Roland's firmware | B: reimplement it (as Munt does for the MT-32) |
|---|---|---|
| What runs | A uPD78312 emulator running the D-50's control ROMs, plus an LA chip emulated at the register level, plus the reverb | Native C for the control logic (envelopes, LFOs, tables, allocation), plus the LA partial generator |
| Faithful in | Everything the firmware does, for free, including the bugs | What was reverse engineered and measured |
| Needs from the user | The control ROM, the wave ROM, the reverb ROM | The wave ROM only (synth partials need nothing) |
| Unknown | How the D-50 talks to its LA chip, register by register; how much of it MAME has; the cost on the pi32v2 | Every curve and table, one by one, against recordings |
| Panel | The D-50's own LCD and buttons have to be mapped to the FM-1's | Our own UI on the FM-1's screen |

**Decided in milestone 1 (RESEARCH.md section 4): B on the device, A on the PC as the answer key.** The device runs our own engine with the
firmware's tables read from the user's EPROM. A PC tool runs MAME's uPD78312 core on the user's ROMs with Nuked-MT32's decap-based LA32, and renders what
the real LA chip would give, so every curve on the device can be tested against it without a real D-50. The PC tool is never linked with the FM-1's
SDK, so its GPL parts are no problem there.

**Munt** (mt32emu, LGPL-2.1+, which can be combined with this repository's GPLv3) emulates the MT-32, a cut-down D-50 with the same LA chip family.
Its LA32 wave generator (synth waves, PCM playback, ring modulation, the log/exp tables) is the best known public reverse engineering of the chip,
and its TVA/TVF/TVP code shows how the MT-32 firmware drives it. The D-50's firmware is not the MT-32's, so the envelopes, the structures and the
parameter map have to be done for the D-50.

## 3. What comes from fm1-sf2 and what goes

Kept (device side, done and tested):
- `fm1_open/` with the SDK, `sdk/Build.ps1`, the JieLi toolchain (`D:\JL\pi32`), `build_fw.ps1`.
- The audio hook in `fm1_open/app/board/audio.c` (`fm1_audio_irq`, 128 stereo Q23 frames a block, `FM1B_SKIP_ENGINE` so the stock FM engine does not run).
- The 32 kHz render path, and the output stage (`sf2out.c`) with its 32 -> 44.1 kHz resampler. *Open: can the codec run at 32 kHz itself, so that
  nothing is resampled?*
- The second core (`cpu1_split.c`): partials are independent, so half of them can render on CPU1.
- The SysEx flash upload (`sf2_upload.c`, protocol `F0 7D 'S' 'F' ...`): it moves the wave ROM, and later patch banks, into the user flash.
- Safe mode, `install.html`, `start_emu.ps1` and fm1-emu, the WebAssembly test harness.

Goes (SF2-specific): the converter (`index.html`, `pack_bank.js`, `convert.py`), the FM1B bank format and `fm1b*.c`, the live cache and MP3,
SEA5/SEA6/BFP8, the MIDI file player and `song.html`, `soundfonts/`, the GM banks and `banks/`, the SF2 tests. They are removed in one commit
once the D-50 engine plays, so that the device side keeps building all the way.

## 4. The budget

- **CPU**: 240 MHz, two cores. In fm1-sf2, 32 BFP8 voices with filter cost about 50-60 % at 32 kHz on one core. A D-50 needs 32 partials, each a
  wave generator (or PCM playback), a resonant TVF and a TVA, plus ring modulation, chorus, EQ and reverb. That should fit on two cores, but nothing is
  measured.
- **Flash**: the user region is 536 576 bytes and the wave ROM is 524 288: it fits, with 12 288 bytes left for the firmware's tables. A bank of
  64 patches (28 672 bytes) does not fit beside it and goes in the image or another region (milestone 5).
- **SRAM**: tight. fm1-sf2 does not boot under 111 468 bytes of heap. The reverb's delay lines at 32 kHz have to fit (fm1-sf2's reverb and chorus take 16 KB).
- **The ROMs are Roland's.** Nothing from them goes into this repository or a release. The user gives the install page the dumps of their own
  D-50's wave ROM and EPROM, and it uploads the wave ROM and the tables it needs, as a bank is uploaded today. Without them, the firmware says what is missing.
- **Licences**: the firmware links the FM-1's closed SDK, and the linking exception covers only code that carries it. Our own code and Munt
  (LGPL) may go into a published firmware. Nuked-MT32 (GPL-2.0+) and PicoFaceD5 (GPL-3.0+) may not, unless their authors grant the exception
  (RESEARCH.md section 3).

## 5. Milestones

Each one is played in fm1-emu before it goes to the device, as in fm1-sf2.

1. **Research**: done 2026-11-19, [RESEARCH.md](RESEARCH.md). Still open: reference recordings of a real D-50 if there is access to one.
   - **1b. The PC reference**: MAME's uPD78312 core on the user's IC25 + IC22, Nuked-MT32's LA32; first to find the firmware's LA32 writes, then to
     render reference notes. Runs beside milestones 2-4.
2. **One synth partial**: square/saw with pulse width, TVA envelope, MIDI note on and off, 32 kHz through the existing hook. Measure its cost.
3. **A whole tone**: two partials, the 7 structures with the ring modulator, TVF with resonance, pitch envelope, the LFOs, key follow, velocity.
   A WebAssembly test for each, as fm1-sf2's `test_filter.js` and `test_lfo.js`.
4. **The patch**: Upper and Lower, the key modes, the voice allocation over 32 partials, CPU1 for half of them.
5. **SysEx**: the D-50's DT1/RQ1 address map; a `.syx` bank loads and plays. Patches in the user flash.
6. **PCM partials**: the wave ROM uploaded to the flash, attack and loop playback as the LA chip does it.
7. **Effects**: EQ, chorus, then the reverb types.
8. **The panel**: patch select, the edit pages on the FM-1's screen and encoders, the 27 keys.
9. **Faithfulness**: A/B against the reference recordings, curve by curve.

## 5b. Where it stands (2026-11-19, branch `d50-engine-port`)

The PicoFaceD5 engine (`third_party/picofaced5`, own use only) plays the D-50's factory bank on the FM-1 firmware in fm1-emu. Not yet on a device.

- **PC**: `tools/d50_host/build_bank.ps1 [-Patches 0,8,...]` renders patches of the bank in `roms/out/d50_pcm.fmd5` to `roms/out/d50_bank_dry.wav`
  (as the FM-1 plays now) and `d50_bank_reverb.wav`. `build.ps1` renders the engine's eight hand-built presets. WASI SDK + Node.
- **Firmware**: `fm1_open/app/d50/` (`d50.cpp` the glue, `d50_inflate.c` the bank's unpacking, `d50_math.c` the libm the SDK lacks, `cxx/` the std
  headers the toolchain lacks). `sdk/Build.ps1` compiles `.cpp` (native, `-Os`). `FM1_D50_ONLY` (fm1b_config.h) makes the FM1B player's
  paths dead code (its audio, bank binding, notes and panel pages): image 450 716 of 453 921 bytes, heap 131 148 (the bank takes 28 KB of RAM).
  Build: **`.\build_d50.ps1`**, two builds as fm1-sf2's workflow makes for its emulator: `dist\d50.fwsc` with both cores for the FM-1 (packed
  with the D-50 data into `dist\install\` for install.html) and then `dist\d50_emu.fwsc` with one core for the emulator (the last build, so
  `start_emu.ps1` runs it; the private page and its save are made from it). The emulator plays better on one core: emulating CPU1 costs the
  computer more. One build by hand: `.\build_fw.ps1 -Name d50 -Rate 32000 -LiveCache:$false -DualCore on|off`.
- **Two cores** (2026-11-19, because the FM-1 stuttered on one): the engine renders a block at a time (`Patch::render_block`): each tone steps
  its LFOs through the block first and keeps their values per sample (`Tone::begin_block`, `LfoSnap`), so every voice can render its whole block
  on its own (`render_voice`), and every second sounding voice goes to the SDK's CPU1 through fm1-sf2's hand-over (`app/cpu1_split.c`,
  `fm1b_split_begin/wait`; not while an upload writes the flash, `fm1b_split_held`); CPU0 then does EQ, chorus, mix and reverb sample by sample.
  The block is cut where a delayed Lower note is due. `tools/d50_host/test_block.cpp`: all 64 patches, blocks of 1..128, the other core's job
  run last: the same output as sample by sample within 1.5e-6 (float rounding of the voices' sum; 8e-5 with the 16-bit reverb, whose rounding
  then flips now and then). The panel says 2 CORES or 1 CORE (CPU1 not up, or it missed 20 ms once and the split was switched off for good).
  In fm1-emu: the info page's `SPLIT ... L0 W200 J595` (CPU1 renders 595 us of each block while CPU0 waits 200), and an eight-note chord on
  Staccato Heaven (16 voices, 32 partials) for 8 s gave no overrun (`OVR 0`; `test_emu/d50_stress.js`). **fm1-emu reads the load low**: the
  one-core build had no overrun there either, though the FM-1 stutters. Whether two cores are enough on the FM-1 is not known yet.
- **The load, after the FM-1 still stuttered on two cores** (build `d50_dual2`, image 452 380, 1 541 bytes to spare):
  - The D-50 page's fourth line is the firmware's own measure: `CPU 53% MAX 65%  OVR 0  LIMIT 16  CPU1 6` = the audio interrupt's share of
    a block on CPU0 (average, highest in the last second), the blocks it overran since start, the guard's cap on each tone's voices, CPU1's
    share of the sounding voices in sixteenths. **fm1-emu's own "load" is its load on the PC (it goes over 100 %), not the firmware's:** the
    numbers in it above (34 %, 60-80 %) are not the FM-1's.
  - Silence costs nothing: a tone with no voice for 0.25 s whose EQ and chorus are under -100 dB skips them (`Tone::finish_sample`, the
    chorus's sweep stands still meanwhile, so it starts at another phase: the same sound, other samples), and the reverb with no send for 0.5 s
    and a wet part under -100 dB passes the dry part only (`Reverb::process`).
  - The CPU guard (`d50_guard`, from `sf2out_load` each block): over 85 % it retires the oldest released voice (20 ms fade, `shed_voice`);
    with none to retire and over 92 %, a lower cap on each tone's voices (`Patch::cap_voices`, down to 4: new notes past it find no slot);
    under 60 % for 0.25 s the cap comes back a voice at a time.
  - CPU1's share follows CPU0's wait (`split_wait`): over 40 us a sixteenth less, under 5 us a sixteenth more (4..13).
  - In fm1-emu, by the firmware's measure: silent 12 %, Staccato Heaven with eight keys (16 voices, 32 partials) 53 % (65 % at most), CPU1
    5-7 sixteenths, no overrun. On the FM-1: not known yet.
- **A private emulator page** (2026-11-19): https://claude.ai/artifact/UGLmXVLVWJn47frK78wd4c (claude.ai, private to its owner). `node
  tools/d50_emu_site.js [fwsc] [fmd5]` makes it in `roms/out/emu-site/`: fm1-emu's files from `emu/` (MIT; `main.js` with three changes for
  claude.ai's frame: no dialogs, no query string in the address, no fetch from the Firmware Hub), a catalog with only the D-50 firmware (as
  base64 text, `d50fw.txt`: claude.ai serves no `.fwsc`) and a page of its own. It holds no Roland data: the script also writes
  `roms/out/d50.fm1save` (the firmware, and the samples and bank as flash sectors at 0x7C000), which one imports with the page's Import...
  into that browser only. The save belongs to that firmware build: a new build needs a new save. Heard playing in claude.ai. Since version 2
  it runs the one-core build (`build_d50.ps1`; the panel says 1 CORE).
- **Upload**: `sf2_upload.c` stops the D-50 before it erases the flash (`d50_unbind`), and its check whether the data is installed (cmd 9)
  takes the D-50's length (`d50_flash_bytes`), so the install page does not send 534 KB again when they match.
- **Reverb**: PicoFaceD5's reverb with its delay lines as 16-bit words (Q15, rounded: `D5_REVERB_INT16`, 42 KB instead of 84) in the engine
  library's two idle effect units (`.bss.fm1_effects`, 48 832 bytes, which `sdk/Build.ps1` marks with `fm1_fx_pool_begin`/`_end` for a D-50 build).
  Two segments around the units' state words (`D5_REVERB_EXTERNAL_POOL`, `d50.cpp attach_reverb`): [0, 24 380) for the allpasses, the entrance
  and the first comb or the tap line (cut to the farthest tap, 10 817 words), [24 384, 48 796) for the other two combs. The firmware never calls
  the library's instrument, so the units are never started; it attaches the reverb only when both state words read -1 (idle), else it stays dry.
  The panel says REVERB or DRY. Against the float reverb on the PC the output differs by 42..53 dB under the wet signal (`build_bank.ps1` renders
  `d50_bank_fm1.wav` beside `d50_bank_reverb.wav`). Bluetooth audio (A2DP) is not touched.
- **Data**: `d5_make_blob.py` on your PCM ROMs, then `node tools/d50_pack.js roms/gen/d5_pcm.bin roms/out/d50_pcm.fmd5 --bank "D50 files/syx files/PND50-00.syx"`.
  The bank (64 patches, 28 672 bytes) is deflated to 9 780 bytes after the samples: 534 088 of the 536 576 bytes of user flash, one bank only.
  The PN-D50-00 dump with Fantasia is `Roland D50/PND50-00.syx` in `rolandd50patches.zip`; `FactoryPatches.syx` is the D-550's factory set.
  It goes to the start of the user flash like a bank: `install.html` and `make_install.js` take it. Without a bank the panel says NO D-50 DATA.
- **fm1-emu** (`.\start_emu.ps1 -Bank roms\out\d50_pcm.fmd5 -Script d50_factory.script -Tap`): the panel shows PATCH 11..88 and the name; MIDI
  program change 0..63 and SELECT choose the patch. Fantasia, Digital Native Dance, Pizzagogo, Glass Voices, Staccato Heaven and Arco Strings sound.
  Load at 320 MHz without the reverb: 34 % silent, 60-69 % with a three-note chord on these (mostly Dual) patches; with it 37-48 % and up to 80 %
  (the state words read -1 in fm1-emu, the panel says REVERB), one core.
  Output about 10 dB lower than with the presets (the engine's headroom for 16 voices).
- **Not yet**: the two-core build heard on the FM-1; if it still stutters: the engine at -O2 for its hot loops (the image has 3 KB left), fewer
  voices, or the voices' code in SRAM. More banks (no flash left), the output level.

### Optimising the engine (2026-11-19, night)

`tools\d50_hostench.ps1 [-Patches 16]` (WASI + Node) plays eight keys on every patch for 4 s through `render_block` and prints the time and an
output fingerprint. Host time per patch fell from 108 to 73 ms (-32 %); the host is not the M33, so the device gain is likely larger (below).

- **The engine ran from flash on the FM-1.** `D5_HOT` and the sin/exp tables only did something with the Pico SDK; on the pi32 toolchain they were
  no-ops, so the whole render loop and its tables competed with the 512 KB sample blob for the XIP cache (the 167 % load story in `d5_hot.h`).
  `d5_hot.h` / `d5_fastmath.h` now put them in `.volatile_ram_code.*` / `.volatile_ram.*` when `__GCC_PI32V2__` is defined. Costs about 11 KB of
  SRAM (heap 131 148 -> 120 140 bytes; the minimum is 111 468). Not measured on a device.
- `SynthPartial::run` / `PcmVoice::run` / `Voice::render`: partials render a chunk (up to one 16-sample control period) with their state in
  locals; `next()` is `run(1)`. Bit-identical output.
- `pow()` per block per square partial replaced by `fast_log2` + `fast_exp2` (libm pow is software on the M33).
- Voice mix constants (balance, ring gain) once per note; patch mix weights once per block; reverb tap positions cached; chorus delay sweep
  (2 sines a voice a sample) every 4th sample, interpolated; flat EQ (both gains 0 dB, an exact identity) skipped; LFOs no route uses are not
  stepped; no clamps in `fast_sin`/`fast_exp2`; `Env5::next` in-segment fast path.
- `tools/d50_host/test_block.cpp` still passes (block vs sample by sample, 9e-5, the 16-bit reverb's rounding).
- **Not done:** the engine is still compiled `-Os` (`sdk/Build.ps1`, whose hash is pinned in `sdk/manifest.json`); `-O2` is probably faster on the M33
  but the image has only ~2.9 KB to spare. Nothing here was run in fm1-emu or on a device.
